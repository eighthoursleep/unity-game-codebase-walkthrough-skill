# game-teach-module：模块教学文档系列生成

把一个代码模块解析成一组教学式 md：`AboutMe/<层名>/<模块名>/README.md` + 编号章节，每份 ≤300 行，由浅入深，读者是熟悉该项目的语言与引擎、但不了解本项目的新客户端程序。全程三个阶段：**快速扫描 → grilling 访谈 → 写作落盘**。

工作方式源自两个上游 skill 的融合，本文件已把它们改写为文档场景，不需要再读原文：

- **grilling**：动手写之前用分轮访谈敲定所有决策。把决策画成设计树，每轮问完当前"前沿"（前置已定的全部问题，编号+给推荐答案），等用户答复后再算下一轮前沿；访谈结束的标志是前沿清空、无隐含假设。
- **i-have-adhd**：读者的工作记忆很小，"知道"和"做到"之间有摩擦，开始是最难的一步，进度必须可见。这条既约束**文档**的写法，也约束**访谈对话**本身。

## 第 0 步：对齐口径

动手前先做三件事，都是读，几分钟内完成：

1. **读样板**：`AboutMe/` 下已有的模块文档系列（其 README + 任一编号章节）是格式的真源——总览怎么写、章节头三行怎么放、锚点怎么标，以它们为基准。若目标层已有别的模块文档系列，也读其 README 对齐该层风格。
2. **查存量**：检查 `AboutMe/<层名>/<模块名>/` 是否已有文档、`AboutMe/` 根下是否有同主题旧单文件（如《XXX模块.md》）。有旧文档则本次遵循"吸收重写 → 新文档声明取代 → 删原件"流程，删除前必须得到用户确认（AboutMe 未纳入 git，删错不可恢复）。
3. **定代码根**：用户没给层名/模块对应的代码目录时，先按现存文档口径推断再向用户确认一句，不要猜完直接开跑。

## 阶段一：快速扫描

目标不是读懂模块，而是**摸出轮廓、攒出值得问的问题**。约束在 20~25 个工具调用内，工程树庞大，绝不通读源码。

1. 优先用项目配置的知识图谱/索引工具（若有）拿结构与调用关系；graph 覆盖不到再用 Glob/Grep 定位、抽样读关键文件（优先读名字像 Manager/Root/Main/Entry 的类）。
2. 扫描产出两样东西：
   - **模块轮廓**：模块干什么、分几个子系统、入口在哪、有无明显死代码；
   - **推荐拆分方案**：章数、每章主题、各章前置依赖、每章预估行数（预估要给具体数字，"大概几章"这种模糊估计没有意义）。

## 阶段二：grilling 访谈

拿着扫描结果开始分轮访谈。对话本身按 adhd 规则塑形：

- 每轮开头一行重述进度（"第 2 轮，共预计 3 轮，拆分方案已定，剩深度与术语"）；
- 每个问题编号、给推荐答案（➡️），推荐必须来自扫描证据，不是拍脑袋；
- 砍支线：中途冒出的次要问题收进"最后一并确认"清单，不插进当前轮；
- 前沿清空后，用一段话复述共识，用户确认后才进入写作。

必须问到的决策（前置已定时才进当轮，未定时排后）：

1. **拆分方案**：章数、主题、顺序、预估行数——按扫描给推荐，用户可增删合并；
2. **读者与深度**：默认"新客户端程序、熟悉项目所用的语言与引擎、不懂本项目"；有特殊读者（如要带服务器视角）在此提出；
3. **取代关系**：是否吸收/删除旧文档（见第 0 步第 2 项）；
4. **术语定名**：模块内的核心概念用文档统一术语还是代码原名（默认代码原名+首次出现给白话解释）；
5. **死代码处理**：就地一行警示+章末汇总清单（默认做法），还是直接略过。

## 阶段三：写作

### 结构

- `README.md`：系列总览——一句话说清、一句话架构、章节地图（章｜主题｜前置 三列表）、阅读路径（30 分钟速览／完整路径／问题导向，给具体章号）、术语速查。
- `01-XXX.md` 起的编号章节，章名是"主题"不是"文件名"。
- **由浅入深的骨架**：前 1~2 章建立全局认知（时间线/总览 ASCII 图+关键类表格），中间章逐子系统深挖，末尾章收横切面/全景/附录。每个抽象**先讲它为什么存在（解决什么问题），再讲怎么实现**——只讲实现不讲动机，读者记不住也不会用。

### 硬约束（AboutMe 既成约定，违反即返工）

- 每章头部三行：`定位`（本章讲清什么）/ `前置`（需先读哪几章）/ `路径约定`（指向 README，不重复抄）。
- 代码路径相对约定的代码根（按 AboutMe 现存口径），例外注明。
- 锚点格式：**`类名.方法名` + 文件路径**，不写行号（代码易动，行号必烂）。
- 章末放「想改 X 看哪里」表（意图 → 文件/类）。
- 死代码就地一行警示，系列末章或附录汇总清单。
- **每份 ≤300 行**，用 wc 核实。超了拆章或砍内容，不要压缩排版硬塞；少于 60 行的章考虑并入相邻章。

### adhd 塑形规则（决定每章的"手感"）

- 每章开头一行"读完你能做什么"（兑现成具体能力："能说出一次技能施放从 UI 到服务器的完整链路"，不是"了解技能系统"）。
- 多步流程一律编号列表，每步一个有界动作，给具体类名/方法名，不写"一些系统""某些地方"。
- 最终可见列表每组 ≤5 条，更多就分组或转表格——表格是教学文档的主力形态，散段落是最后手段。
- 每章末一行"下一步"：读哪章，或一个可动手的验证动作（"打开 `XxxManager` 对照第 3 节走一遍主循环"）。
- 章与章之间的衔接靠兑现：上一章末尾预告的"下一步"就是下一章开头的"定位"，读者每停一次都能捡得起来。

### 收尾

1. 每份文档按硬约束逐条自检（锚点、路径、三行头、行数）。
2. 在 `AboutMe/Overview.md` 第 5 节登记新系列链接。
3. 若用户确认删除旧文档：声明取代关系写在 README 头部引语，删除后回复里列出删除清单。
4. 回报时按 adhd 规则：先说"现在能用了什么"（文档落在哪、从哪章开始读），列产出清单，给一个下一步动作。

## 边界与禁止

- 只产出 `AboutMe/<层>/<模块>/` 下的文档系列；不生成模块清单（`game-module-overview`），不生成全项目总览（`game-client-overview`），不修改代码。
- 不通读源码、不逐文件罗列——教学文档讲机制与链路，不是目录转述。
- 不在未获用户确认时删除任何文件；不动 `AboutMe/` 之外的目录。
- 访谈轮次原则上 ≤3 轮：前沿问题尽量在扫描后合并成大轮，用户明确表示"就按推荐来"时立刻收口开写。
