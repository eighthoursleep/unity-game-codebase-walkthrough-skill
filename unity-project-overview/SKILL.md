# Unity 项目全景总览（一级模块 + 模块依赖架构文档）

## 目标
对当前 Unity 项目进行扫描，识别出**一级模块**（粗粒度功能域），并**重点梳理一级模块之间的依赖关系**，生成一份项目架构分析文档。本文档是后续技能（module-overview）的输入：通过它确定"有哪些一级模块"以及"它们之间如何依赖"。

**本文档只负责"一级模块层"——列出模块并刻画模块间依赖，不深入到具体子模块细节。**

## 前置依赖
- 若已指定 Unity 项目路径则直接使用，否则以当前目录为项目根目录。
- 若已知模块边界信息，可据此辅助划分一级模块。

### 6. 一级模块列表 + 模块间依赖关系（**核心章节**）
这是本文档最重要的章节，也是 Skill 2（module-overview）的输入接口。粒度控制：一级模块数量控制在 **5-10 个**，避免过细。

**一级模块划分判定规则（内置规范，随本技能分发）**——权威母本维护于 `ClaudeSkills/_shared/module-division-guide.md`，本段为其随包副本；复制到其他环境后母本不可达时，按本段执行即可：
- **按逻辑职责划分**，不按文件/类逐个拆。
- **同类前缀归并**：类名前缀/命名空间相同的一组类 = 同一模块的不同部分，必须归并、不得拆多。如 `BattleMgr`/`BattleState`/`BattleObstacle` 同属"战斗模块"，不识别成 3 个。
- **判定优先级**：逻辑职责 → 类名前缀/命名空间 → 目录结构（目录仅供参考）。
- **模块大类**（标注属性，非重划分）：**B**=底层 / **F**=框架 / **A**=应用。

#### 6.1 一级模块清单
> 每个模块需标注**大类**（B=底层 / F=框架 / A=应用），判定沿用共用规范《模块/系统划分原则》第 5 节。
> 大类是"标注属性"：不因分层拆开同类前缀的模块，只作为每个模块的一个维度列。

| 模块名称 | 大类 | 对应目录路径 | 核心职责（一句话） | 依赖关系 |
|------|------|------|------|------|
| 业务模块 | A | Assets/Scripts/Game | 核心玩法与逻辑 | 依赖网络模块（调发送协议接口） |
| 热更新模块 | F | Assets/Scripts/Hotfix | 资源与代码热更新 | 依赖业务模块（读配置） |
| 网络模块 | B | Assets/Scripts/Network | 底层网络通信 | 无依赖（底层） |
| ... | ... | ... | ... | ... |

**依赖关系列**：每条写明**方向 + 内容（依赖对方哪些能力）+ 强度**（强依赖 / 弱解耦 / 经事件机制），判定必须基于代码中的实际引用（using、require、import、assembly 引用、接口调用），不得猜测。

#### 6.2 模块间依赖关系（重点）
> **流向审视**：理想依赖方向为 应用(A)→框架(F)→底层(B)。发现反向依赖（框架依赖业务 / 底层依赖业务）时，在"关键发现"中标注为架构警讯。

依赖关系已在 6.1 表格的"依赖关系"列逐条写明（方向 + 内容 + 强度），本节补充全貌：
- 用箭头图呈现依赖链，例如：`业务模块 → 网络模块 → 热更新模块`。
- 关键标注：循环依赖、单例贯穿引用、事件总线解耦等结构性特征。

> **给下游的一句话**：本节 6.1 的"一级模块清单"就是 module-overview 技能的输入项——用户选定其中某个模块名称后，module-overview 会深入该模块内部梳理其子模块与依赖。

### 7. 启动流程

### 8. 关键发现摘要（设计亮点 / 权衡 / 风险点）
- **设计亮点**：列出 3-5 个值得学习的架构优点
- **值得关注的权衡**：列出 2-3 个设计取舍
- **风险点**：列出 2-3 个潜在技术风险或代码质量问题（**特别关注模块间的循环依赖、过度耦合、单向依赖被破坏等情况**）

## 执行步骤
1. **信息采集**：
   - 读取 ProjectSettings/ProjectSettings.asset 获取 Unity 版本
   - 读取 Packages/manifest.json 获取依赖包信息
   - 扫描 Assets/ 目录结构，识别顶层目录
   - 对核心代码目录递归扫描，识别子目录结构
   - 通过文件名/类名/命名空间推断技术选型
2. **识别一级模块**：
   - 按功能域粗粒度划分 5-10 个一级模块
   - **按逻辑职责 + 类名前缀/命名空间聚合**：前缀相同的一组类归并为同一模块（如 `Battle*` 各分件同属战斗模块）
   - 识别启动入口文件、框架类型、热更新/资源管理方案
3. **梳理模块间依赖**（核心步骤）：
   - 对每一对模块，检查代码中的 using/require/import、assembly 引用
   - 标注依赖方向、依赖内容、依赖强度
   - 检查是否存在循环依赖或异常耦合，写入"关键发现"
4. **文档生成**：
   - 仅生成一个文件：`项目根目录/AboutMe/Overview.md`
   - 确保 6.1 的"一级模块清单"清晰可用，供 module-overview 技能引用

## 约束
- 必须输出完整的架构分析文档，内容详实
- 所有技术栈与依赖判断必须基于实际代码扫描，不得猜测
- 模块间依赖关系需基于代码中的实际引用推断
- **本文档边界 = 一级模块层**：只列出一级模块 + 模块间依赖，不深入某一个模块内部子模块
- 只允许修改/创建 `项目根目录/AboutMe/Overview.md` 这一个文件
- **同名冲突防护**：生成前检查 `项目根目录/AboutMe/Overview.md` 是否已存在。若已存在且非本模块产出，**先向用户确认**再覆盖，不得静默覆盖他人文件。
- **中文行文约定**：禁止长串的句子，或把几个句子连在一行/一段。必须**一句话一行**；即使描述一件事用了一个长句，也要拆成多行单句。表格单元格、步骤概括、职责边界、清单项的表述均适用。
