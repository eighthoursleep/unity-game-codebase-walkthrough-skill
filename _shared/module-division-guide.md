# 模块/系统划分原则（统一说明）

> 本文档是 `unity-project-overview`、`unity-module-overview`、`unity-module-detail` 三个技能**共用**的模块划分规范。
> 三个技能在划分模块/系统、子模块/子系统时，一律遵循本原则，**不得各自内联另立标准**。
>
> 引用方式：各 SKILL.md 在"划分判定规则"处统一注明"遵循《模块/系统划分原则》"，并将核心要点随附一行，供速览；完整规则以本文档为准。

---

## 一、核心总原则

**模块 / 系统、子模块 / 子系统一律按"逻辑职责"划分，而非按文件或类逐个拆分。**

模块与模块、子模块与子模块之间的边界，由"这一组代码共同承担什么职责"决定，不由"这个文件在哪个目录""这个类叫什么文件名"决定。

---

## 二、最关键的判定规则（同类前缀归并）

> **类名前缀（或命名空间）相同的一组类，属于同一个模块的不同部分，必须归并为一个模块，不得识别成多个模块/系统。**

典型例子：

| 类组成员（前缀相同） | 归属 |
|------|------|
| `BattleMgr` / `BattleState` / `BattleObstacle` / `BattleScore` | 同属 **战斗模块** |
| `LoginCtrl` / `LoginView` / `LoginData` / `LoginProxy` | 同属 **登录模块** |
| `PetMgr` / `PetData` / `PetConfig` / `PetView` | 同属 **宠物模块** |
| `BagCtrl` / `BagData` / `BagView` | 同属 **背包模块** |

> **易错点**：`BattleCtrl`、`BattleView`、`BattleData` 常被误当作 3 个模块。它们共同服务"战斗"这一职责，是**同一模块的三部分**（控制/表现/数据），必须归并为 1 个"战斗模块"，其内部的分件关系由 unite-module-detail 剖析核心逻辑时体现。

---

## 三、判定依据优先级

当需要判断"这是同一模块的两部分，还是两个独立模块"时，按下述优先级判定：

1. **逻辑职责**（最高）：共同服务于同一职责 → 同一模块。
2. **类名前缀 / 命名空间**：前缀相同往往是同一逻辑族群，倾向归并。
3. **目录结构**（最低，仅参考）：同一逻辑模块可能散落于多个目录或多个文件，**不能只凭目录拆分**。

> 疑问时的自检问题：**"这些类是否共同服务于同一职责？"** 是为同一模块，否则才是不同模块。

---

## 四、粒度与边界

- **一级模块**（project-overview 产出）：粗粒度功能域，数量控制在 **5-10 个**。一个一级模块通常是一个完整业务域。
- **子模块 / 子系统**（module-overview 产出）：承接某一级模块内部，按逻辑职责聚合而成的一个整体（通常为一类前缀相同的类群）。
- 只有职责确实独立（如**红点系统**、**网络底层**、**配置管理**这类横切/基础设施）才单独建模，不强行归入业务域。
- 允许"一个逻辑模块 = 内部再分若干分件"，但分件不是独立模块。

---

## 五、模块大类（底层 / 框架 / 应用）

识别模块时，除所属**逻辑领域**外，还必须标识其**大类**——该模块在项目分层中所处的层面。共三大类：

### 5.1 三大类定义
| 大类 | 标记 | 含义 | 典型例子 |
|------|------|------|------|
| **底层模块**（基础设施） | B | 几乎被全员依赖、自身几乎不依赖别人，跨领域通用 | 网络、资源管理、序列化、本地化、日志、工具库、数据持久化 |
| **中间框架模块** | F | 业务无关的通用框架/中间件，为业务提供支撑，可依赖底层 | 事件系统、UI 框架、对象池、MVC 基类、异步框架、配置/红点系统 |
| **顶层应用模块**（业务） | A | 具体玩法/功能，依赖框架与底层 | 战斗、背包、登录、任务、角色养成 |

### 5.2 判定要点
- **看依赖方向定类**：底层几乎只被依赖；应用大量依赖他人、少被他人复用；框架介于其间为应用服务。依赖方向是定类的第一依据。
- **每个模块归入唯一一大类**；若横跨（既有框架性质又被业务持有），以其主要服务对象定类。
- **大类是"标注属性"，不是重划分**：不因分层拆开同类前缀的模块，也不把不同职责强行合并；它只是每个已识别模块的一个维度列。

### 5.3 产出要求
- 在各级模块清单中为每个模块/子模块增加**"大类"列**，标注 **B / F / A**（可附一句话理由）。
- 依赖关系刻画时顺带审视流向是否合理：**应用(A)→框架(F)→底层(B)** 为理想单向；反向依赖（框架依赖具体业务、底层依赖业务）常是架构警讯，写入"关键发现"。

## 六、判定的最终产出形式

- 划分结果为一张**逻辑模块清单**（配目录路径、核心职责、代表类名），供下游技能输入。
- 模块之间的依赖关系单独刻画（依赖方向、内容、强度），与划分本身分离。
